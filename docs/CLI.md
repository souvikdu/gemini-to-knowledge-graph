# CLI Reference

Every stage is resumable — interrupt and re-run any script and it picks up
where it left off.

---

## `classify_chats.py`

- `python classify_chats.py` — classify everything not yet classified
- `python classify_chats.py 20` — classify only the next 20 (useful for testing your prompt/taxonomy)
- `python classify_chats.py --retry` — re-attempt only chats that previously errored

**Resume intelligence:** skips chats whose `chat_fingerprint()` hasn't
changed since last classified.

---

## `obsidian_layout.py`

- `python obsidian_layout.py` — incremental: writes only new or changed conversation notes, refreshes all topic/category hubs
- `python obsidian_layout.py --force` — wipes and regenerates everything. **Use this after editing `config/topics.json`** (renaming/merging topics) — incremental mode never deletes stale topic/category notes on its own.

**Resume intelligence:** goes further than the classifier, comparing a
`note_signature()` — content hash *plus* classification outcome — so a
chat whose text is unchanged but whose classification just went from
`error` to `ok` (or from unclassified to classified) still gets its note
rewritten, instead of silently staying stale.

---

## `embed_chats.py` (Optional)

- `python embed_chats.py` — embed all classified chats with `status == "ok"` whose embedding is missing or stale, then rebuild top-K `similarity_links`.
- `python embed_chats.py 20` — embed only the next 20 chats (useful for smoke-testing endpoint setup or latency).
- `python embed_chats.py --recompute-links` — skip all embedding API calls and recalculate `similarity_links` directly from vectors already stored in SQLite. Use this after adjusting `top_k` or `min_similarity` in `config/embedding.json`.

**Resume intelligence:** compares a `summary_signature` (sha256 hash of `truncate_title(title) | summary | model`) against stored `embeddings.summary_hash`. Chats whose summary text or active embedding model haven't changed are skipped without making API calls.

---

## `embedding_layout.py` (Optional)

- `python embedding_layout.py` — incremental: writes only new or modified conversation notes in `Similarity_Vault/Conversations/`, skipping notes whose `similarity_note_signature` hasn't changed.
- `python embedding_layout.py --force` — wipes and regenerates `Similarity_Vault/Conversations/` completely.

**Resume intelligence:** computes a `similarity_note_signature` incorporating the summary hash, current similarity-link neighbors/scores, and transcript turns. A note is only rewritten if its content, neighbor links, or underlying turns change.

---

## `python -m extractors.gemini`

No flags — incremental based on the last-seen pagination timestamp, and
always skips conversation IDs in the ignore list (populated by
`prune_chats.py`). Reconciles pin status changes automatically.

---

## `prune_chats.py`

- `python prune_chats.py` — scan `chats/` for orphaned conversations (files no longer on disk but still tracked in the DB) **and** any chats marked `DEL` in the review manifest, if one exists (see [Reviewing extracted chats](#reviewing-extracted-chats)). **Dry-run by default** — prints what would be deleted without changing anything.
- `python prune_chats.py --prune` — execute the deletion after reviewing the dry-run output. For each candidate the cascade is: delete classifications → delete embeddings → delete similarity links → delete `chats` row → add to ignore list → delete vault notes (cleaning both `Obsidian_Vault/` and `Similarity_Vault/` if configured). For manifest-marked chats, the JSON file itself is also deleted (safely — see below) before this cascade runs.
- `python prune_chats.py --prune --confirm-large-delete` — bypass the 30% safety gate if candidates exceed that threshold (e.g. after a bulk cleanup).
- `python prune_chats.py --list-ignored` — show all currently ignored conversation IDs with their reason and timestamp.
- `python prune_chats.py --unignore <cid> [<cid> ...]` — remove conversation IDs from the ignore list. The chats will be re-downloaded on the next extraction **only if** a new message has pushed the chat past the current pagination checkpoint; otherwise you'll need to reset `last_timestamp_regular` to `0` in `checkpoint/extraction_state_gemini.json` to force a full re-scan. Their old classification and vault note are **not** restored — those must be regenerated by re-running the full pipeline.

A review-marked chat's JSON file is only deleted after its `source_file` path
is resolved from the DB, verified to stay inside `chats_dir`, confirmed to be
a real `.json` file, and confirmed to have a matching `conversation_id` inside
it — a filename is never trusted directly from the manifest. If a chat is
deleted between generating the manifest and running `--prune`, it's reported
as a stale `DEL` row and skipped, not treated as an error.

## Reviewing extracted chats

There are two ways to decide what gets classified and vaulted — you can use
either one on its own, or both together:

1. **Manual file deletion** — `chats/*.json` is human-reviewable; just delete
   any file you don't want kept.
2. **`review_chats.py`** — generates an editable CSV manifest so you can skim
   titles (and automatically-flagged sensitive content) without opening a
   single chat file, then mark rows for removal.

Both paths converge on the same place: **`prune_chats.py` is the only thing
that actually deletes anything.** Marking a chat `DEL` in the manifest, or
deleting its JSON file by hand, doesn't remove any data by itself — it only
stages that chat as a candidate. Nothing is gone until you run
`prune_chats.py --prune`.

### `review_chats.py`

- `python review_chats.py` — generate or refresh `review/chats_to_review.csv`. Automatically scans new and content-changed chats for sensitive info if `config/sensitive_patterns.json` exists (see [CONFIGURATION.md](CONFIGURATION.md#sensitive-pattern-scanning-configsensitive_patternsjson)). Safe to re-run any time — existing `reviewed`/`action` decisions are preserved.
- `python review_chats.py --scan-sensitive` — force a full re-scan of **every** chat against the current rules, regardless of whether content changed. Use this after editing `config/sensitive_patterns.json` — the default incremental scan only re-checks new/changed chats, so edits to your pattern file won't retroactively apply to unchanged chats until you run this.
- `python review_chats.py --mark-reviewed` — after showing a summary of how many chats are `NO`/`RE-REVIEW`/`YES`, prompts for confirmation, then collapses every `NO` and `RE-REVIEW` row to `YES` in one shot. Does not touch the `action` column.
- `python review_chats.py --mark-reviewed -y` — same as above, but skips the confirmation prompt. Useful for scripting or CI.
- `python review_chats.py --show-sensitive <conversation_id>` — print the matched context (line + surrounding text) for every sensitive-pattern hit in one chat, so you can judge whether a flag is a real match or noise (e.g. a phone-number regex catching a log timestamp).
- `python review_chats.py --show-sensitive-all` — same as above, but for every chat currently flagged in the manifest.
- `python review_chats.py --mask-sensitive` — preview which reviewed-and-kept chats would have their sensitive spans redacted.
- `python review_chats.py --mask-sensitive --apply` — redact matched sensitive spans directly in the chat JSON files (title + turn text), update the content hash, and clear the manifest flags. Replaces the sensitive text with ``[REDACTED:{alias}]`` (or ``[REDACTED:credit_card ...XXXX]`` / ``[REDACTED:email domain=...]`` for partial masks).

### The manifest: `review/chats_to_review.csv`

One row per chat, columns: `updated_at, source, conversation_id, content_hash, reviewed, action, title, flags`.

**`action` — `KEEP` or `DEL`.** New chats default to `KEEP`. Change to `DEL`
to mark a chat for removal on the next `prune_chats.py --prune`. There's no
third value — a blank or malformed cell is rejected outright rather than
silently treated as either value, so a stray edit can't accidentally stage or
un-stage a deletion.

**`reviewed` — `NO`, `YES`, or `RE-REVIEW`.**
- `NO` — never reviewed. All newly-discovered chats start here.
- `YES` — reviewed and settled; set via `--mark-reviewed` (or by hand).
- `RE-REVIEW` — was `YES`, but something changed since: the chat's content
  changed, or its sensitive-info flags changed (e.g. a full `--scan-sensitive`
  run surfaced a new hit). This is **not** the same as `NO` — it tells you
  "you already looked at this once, but look again," rather than "you've
  never seen this." `action` is left untouched when a row moves to
  `RE-REVIEW`, so a chat you'd already decided to `KEEP` doesn't silently
  become a deletion candidate just because it drifted.

Running `--mark-reviewed` collapses both `NO` and `RE-REVIEW` back to `YES`
in the same pass — you don't need to clear a growing backlog of `RE-REVIEW`
rows one at a time.

**`flags`** — comma-separated alias names from `config/sensitive_patterns.json`
(e.g. `email,phone`), populated automatically. Only alias names ever appear
here or anywhere else the manifest is displayed — never the literal matched
text. Use `--show-sensitive <id>` to see the actual matched context for one
chat when a label alone isn't enough to judge it.

**Row order** is newest-first by `updated_at` (not `created_at`), specifically
so the manifest lines up with Gemini's own conversation sidebar, which also
orders by most-recently-active chat. A chat that gets a new message today
moves back toward the top the next time you regenerate the manifest, the same
way it would in Gemini's UI.

### Recommended workflow

```
extract → review_chats.py → mark DEL rows and/or delete files by hand →
  prune_chats.py (dry-run) → prune_chats.py --prune →
  review_chats.py --mask-sensitive --apply → classify → vault
```

Insert ``review_chats.py --mask-sensitive --apply`` between prune and classify
if you want to keep chats that have sensitive info but redact it before
classification. The content-hash change from masking triggers automatic
reclassification and vault-note rewrite on the next pipeline runs.

You can also prune mid-pipeline any time — the classification and vault
stages call `sync_chats_to_db()` automatically, so the DB is always current
when prune runs. And you don't have to use the manifest at all: manual file
deletion followed directly by `prune_chats.py --prune` still works exactly
as before.

- **File timestamps match conversation time.** The extractor sets each
  file's on-disk mtime to the conversation's own timestamp, so newest-first
  ordering in Windows Explorer or VS Code's file explorer reflects true
  chronological order within and across runs.

- **Deleting a chat before it's ever classified still works.** The `chats`
  metadata table tracks every conversation ID the extractor has ever
  downloaded. When you delete a chat file (or mark it `DEL` in the manifest)
  and run `prune_chats.py --prune`, it removes its metadata and adds it to
  the ignore list — regardless of whether it was ever classified. The
  conversation won't reappear on subsequent extractions.

- **Prune is always a dry-run by default** (without `--prune`). Add
  `--confirm-large-delete` if the number of candidates exceeds 30% of known
  chats — this prevents accidentally wiping your entire DB from a
  misconfigured path, a bad bulk `DEL` edit, or an over-eager pattern match.

## Troubleshooting

The scripts try to fail with an actionable message rather than a bare
traceback. Common ones:

| Symptom | Fix |
|---|---|
| `Missing config file: config/config.json` | `cp config/config.example.json config/config.json`, then edit it |
| `config/config.json is missing paths.{...}` / `api.{...}` / `limits.{...}` | Compare against `config/config.example.json` and add the missing key |
| `config/config.json is missing or has malformed node_sizing...` | Add the full `node_sizing` block — see [CONFIGURATION.md](CONFIGURATION.md#node-sizing-node_sizing) |
| `GEMINI_1PSID and/or GEMINI_1PSIDTS not found in .env` | Re-copy the cookies from gemini.google.com's DevTools → Application → Cookies |
| `Connection failed` / cookies expired | Re-login to gemini.google.com and update `.env` |
| `API not reachable` (Stage 2) | Your LLM server isn't running, or `api.url` is wrong |
| A chat repeatedly fails classification | Run `classify_chats.py --retry` after fixing your LLM config. If it still fails, check the model's output format against the `Category:`/`Topic:`/`Summary:` template, or try a lower `temperature`. |
| Renamed/merged a topic in `topics.json` but old notes remain | Run `python obsidian_layout.py --force` |
| A chat I deleted keeps reappearing after a later extraction | Delete the chat file and run `prune_chats.py --prune` to add it to the ignore list. The extractor will skip it from then on. See [Reviewing extracted chats](#reviewing-extracted-chats). |
| I accidentally pruned a conversation and want it back | Run `prune_chats.py --unignore <cid>` to remove it from the ignore list. Re-download depends on whether a new message has bumped the chat past the current checkpoint — if not, reset `last_timestamp_regular` to `0` in `checkpoint/extraction_state_gemini.json` to force a full re-scan. Re-run classify and vault afterwards — the old classification and vault note are **not** restored. |
| Two topics produce the same filename (e.g. "Data Science" vs "Data science") | Simply re-run `python obsidian_layout.py`. The global collision pre-pass resolves it automatically — no re-classification needed. |
| `obsidian_layout.py` fails with `"Category name collision:"` | Two categories in `config/topics.json` map to the same safe filename. Rename one of them and re-run. |
| `review_chats.py` says the manifest is missing/invalid | If missing, just run `python review_chats.py` to generate one. If invalid (malformed CSV, duplicate ID, bad `reviewed`/`action` value), the error names the specific problem — fix it by hand in `review/chats_to_review.csv`, or delete the file and regenerate (you'll lose existing `reviewed`/`action` marks). |
| A chat stays stuck on `RE-REVIEW` no matter how often I regenerate the manifest | Regenerating never clears `RE-REVIEW` on its own — that's the point, it's a "look again" flag, not something that resolves itself. Either run `python review_chats.py --mark-reviewed` to confirm and clear it (along with every other pending row), or edit its `reviewed` value to `YES` by hand. |
| `--scan-sensitive` says the sensitive config is missing | `cp config/sensitive_patterns.example.json config/sensitive_patterns.json`, then edit it — see [CONFIGURATION.md](CONFIGURATION.md#sensitive-pattern-scanning-configsensitive_patternsjson). Without this flag, `review_chats.py` runs fine with no scanning at all; the flag is only required for a forced full re-scan. |
| A `flags` value I expected to update after editing `sensitive_patterns.json` didn't change | Editing the pattern file doesn't retroactively re-flag chats whose content hasn't changed — only new/changed chats are auto-scanned. Run `python review_chats.py --scan-sensitive` to apply your edits across the full existing history. |
| `credit_card` flags still show false positives from before the tightened regex + Luhn check | The Luhn validator and new pattern only apply to *future* scans. Run `python review_chats.py --scan-sensitive` to re-scan all chats with the updated rules and clear stale flags. |
| `review_chats.py` fails with a `PermissionError` writing to `review/chats_to_review.csv` | The CSV file is open in another application (e.g. Excel, Google Sheets, or a text editor). Close the file and try again. |
| `--mask-sensitive` says no chats would be masked, but `--scan-sensitive` reported flags | Masking only considers `reviewed == YES` + `action == KEEP` rows. A flagged chat still at `NO` or `RE-REVIEW` won't be touched — check that row's `reviewed` column. |
| A chat still shows flags after `--mask-sensitive --apply` | Logged as a warning when it happens — means a pattern didn't fully cover the matched text. Check with `--show-sensitive <id>` and consider tightening that pattern. |
